# FAIRSHIFT — AUTONOMOUS DEVELOPMENT TOOLING SETUP

You are responsible for preparing your own development environment before implementing FairShift. Do not merely recommend tools or give me installation instructions. Inspect the environment, discover relevant tools, install and configure the compatible ones where possible, verify that they work, and then proceed with implementation.

## 1. Understand the project first

FairShift is an SDG 8 hackathon project featuring:

- A premium, responsive worker dashboard.
- An employer/admin dashboard.
- An interactive top-down pixel-art workplace simulation using Phaser.
- AI personas and specialised agents investigating workplace problems.
- Wage transparency, overtime detection, safety reporting, fatigue alerts, and grievance resolution.
- Voice interaction using Vapi.
- Tamil and English accessibility.
- A shared Supabase/PostgreSQL backend.
- Mandatory final deployment to Google Cloud Run.

The final product must have at least three working features, two interfaces, and two industry configurations.

## 2. Inspect the environment

Before installing anything:

1. Inspect the repository and identify the operating system, shell, package manager, runtime versions, and current project structure.
2. Check whether Claude Code, Git, Node.js, npm or pnpm, Docker, Google Cloud CLI, and relevant browser-testing tools are installed.
3. Inspect existing Claude Code plugins, skills, MCP configurations, project instructions, and available repository tools.
4. Identify which credentials and service accounts are already configured without printing their secret values.
5. Check the available disk space and avoid unnecessary installations.
6. Preserve existing project work and configuration.

Do not assume a tool is missing without checking.

## 3. Automatically discover and install the required skills

Prioritise the following capabilities.

### A. Engineering workflow

- Addy Osmani's agent-skills: https://github.com/addyosmani/agent-skills
- Vercel Labs Find-Skills: https://github.com/vercel-labs/skills

Use them to improve planning, code review, testing, and skill discovery.

### B. UI/UX quality

Evaluate:
- Hallmark: https://github.com/Nutlope/hallmark
- Impeccable: https://github.com/pbakaus/impeccable
- SkillUI: https://github.com/kachamo/SkillUI
- UI UX Pro Max.

Choose complementary tools rather than installing every competing design skill. Establish one primary design direction and use additional tools only when they add clear value.

### C. Documentation

Configure Context7 where available:
https://context7.com/docs/overview

Use current documentation for Next.js, Phaser, Supabase, Vapi, Tailwind CSS, and other selected libraries. Do not rely on outdated APIs or invented methods.

### D. Testing

Set up Playwright:
https://playwright.dev/agent-cli/quick-start

Verify that browser automation works. Add suitable test coverage for navigation, core workflows, permissions, and the simulation.

### E. Backend

Evaluate the official Supabase MCP integration:
https://supabase.com/docs/guides/ai-tools/mcp

Configure it only if compatible and useful. Use least-privilege credentials and restrict access to the intended project. Prefer migrations and reviewed schema changes over unreviewed destructive database operations.

### F. Independent code review

Evaluate the OpenAI Codex plugin for Claude Code:
https://github.com/openai/codex-plugin-cc

Install it only if it is compatible with the current environment and provides a useful independent review capability. Do not make the project depend on it.

### G. Security

Evaluate Claude Security and Strix for defensive security testing. Inspect their actual repositories, installation instructions, permissions, and compatibility before use.

Only test systems and environments we own or are authorised to test.

## 4. Decide what NOT to install

Do not automatically install every tool from my research list.

Specifically:

- Do not install both FreeLLMAPI and OmniRoute unless there is a demonstrated reason.
- Do not install Expo Skills for a web-only application.
- Do not introduce Three.js or img2threejs for the core 2D Phaser simulation.
- Do not introduce Composio, Favstash, Google Workspace CLI, or Apify MCP unless a concrete requirement justifies them.
- Defer HyperFrames until the application works and a promotional video is actually needed.
- Avoid duplicate animation libraries and competing UI systems.
- Do not use tools with incompatible licenses or unclear provenance without reporting the issue.
- Do not install unrelated dependencies simply because they appear in a recommended list.

## 5. Installation and configuration policy

For each selected tool:

1. Inspect its official repository, README, installation instructions, package metadata, and license.
2. Check compatibility with the current environment.
3. Prefer official installation methods and pinned, compatible versions where practical.
4. Install it using the appropriate package manager or Claude Code plugin/skill mechanism.
5. Configure required project-level settings.
6. Verify installation and run a small functionality check.
7. Record the installation and configuration in a tooling manifest.
8. Explain any authentication or permission requirement that cannot be completed automatically.

For Claude Code plugins, inspect the plugin and its permissions before enabling it. Use the appropriate marketplace and plugin installation mechanism supported by the installed Claude Code version.

For skills, use the actual supported skill installation mechanism. Do not assume that cloning a repository automatically activates its skills.

For MCP servers, verify the executable, configuration, required environment variables, and connection status. Never fabricate a successful connection.

For npm packages, use the appropriate package manager and update its lockfile. Avoid installing global packages when a project-local dependency is sufficient.

For external services, create setup instructions and environment-variable placeholders when credentials are unavailable. Do not invent credentials or silently substitute fake integrations.

## 6. Autonomous permission and safety rules

You may automatically:
- Inspect files and tool versions.
- Install ordinary project dependencies.
- Add compatible, low-risk development tooling.
- Create project-local configuration.
- Create scripts and tests.
- Configure local browser testing.
- Generate migrations without applying destructive changes.
- Run builds, tests, linting, and type checks.

You must request my approval before:
- Spending money or activating paid services.
- Changing cloud billing or account permissions.
- Deleting databases or existing data.
- Applying destructive migrations.
- Publishing the repository or deploying publicly for the first time.
- Modifying global settings with significant side effects.
- Granting tools broad access to credentials or unrelated files.
- Performing irreversible Git history changes.

Never expose secrets in logs, code, terminal output, or reports.

If a tool requires my login, API key, OAuth consent, or manual approval, finish every other possible setup task first. Then request only the specific intervention needed.

Create or update `CLAUDE.md` so future Claude Code sessions understand:

- Testing and validation commands.
- Security and secret-handling rules.

Do not store secrets in the manifest.

4. Verify available Supabase tooling without making destructive database changes.

Then continue to Phase 0 of the FairShift implementation plan automatically, using the verified tools.

Do not stop after merely printing a plan. Execute all safe and authorised setup steps.

If a particular tool is unavailable, continue with the best verified alternative. Never claim an installation or test succeeded unless you verified the result.

**Your objective is to autonomously prepare the best practical development environment and build FairShift with it, while keeping security, compatibility, cost, and reliability under control.**
